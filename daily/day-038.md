# Day 038: The failure that finishes green

**Wed 2026-07-29 · Enable · Day 38 of 49**

When an automation calls a model and the model gets it wrong, the run usually still succeeds. The
schema validates, the field is populated, and every step downstream does exactly what it was told.
Nothing raises, nothing alerts, and none of the numbers this repo already defines can tell that run
apart from a right one. So the decision about where a person looks at model output cannot wait for a
failure to ask for it.

## Shipped

[enablement/where-a-human-stays-in-the-loop.md](../enablement/where-a-human-stays-in-the-loop.md):
a guide that turns the vaguest line on
[the review checklist](../governance/ai-build-review-checklist.md), the gate a build passes before it
goes live, into something a reviewer can be wrong about. That line reads "a person is in the loop
wherever the stakes are real," and the checklist opens by saying two people running it should reach
the same decision, which that line cannot deliver. The guide replaces it with two questions answered
while the model step is being built: what undoing a wrong output would take, and whether anything
downstream would notice it was wrong. A grid turns the two answers into one of four placements, from
a machine check with no person on it to a person approving every output before it acts. The choice
gets written next to the build, one line with both answers, the routing rule, and the volume it was
chosen at, the same way section 8 of [the automation standard](../standards/automation-standards.md),
the bar every build here is judged against, already has an owner recorded there.

It also went into [the review-loop index](../sops/the-review-loop-in-order.md), the start-here page
that orders every piece of the review system, under both the builder's row and the reviewer's, and
the opening tally went from eighteen pieces to nineteen. That is the edit the index check has been
running in CI since yesterday to catch, and running it locally first is cheaper than reading a red
build.

## What I learned

The instinct, looking at "wherever the stakes are real," was to write a better definition of real
stakes. That was the wrong move, and it took a while to see why. Stakes are a fact about
consequences, and consequences live outside the build, so no rewording lets a reviewer answer that
line from the thing in front of them. The information does exist. It exists earlier, with the person
designing the step, who knows what the output touches and what undoing it would cost. So the fix was
never a sharper wording. It was moving the decision to where the answer already sits, and leaving the
reviewer a written claim to test instead of a judgment to make. The general form is worth keeping:
when a check cannot be answered from the thing being checked, move the decision rather than the
wording.

The second thing was cheaper to learn and more embarrassing. The guide argues that a wrong model
output scores as a clean run, which is true, and then prescribes putting a person on some of those
runs, which turns them into exceptions by construction. A build with a person approving every output
posts an exception rate near one hundred percent while working exactly as designed. The claim and the
remedy pull on the same number in opposite directions, and the draft did not notice until it was
checked. The file now says what that number means on such a build.

## Next

The two answers are given about a model step as it stands today, which quietly means as its prompt
and its model stand today. Both of those change without ceremony: someone rewords the instruction,
someone swaps to a newer model, and the step now decides differently while the placement recorded
next to it still describes the old one. A placement is a claim about a version nobody is currently
tracking. So the next piece treats prompts and model choices as what they are, configuration, with
the same versioning, review, and change record any other production configuration gets.

Behind that sits the question this guide deliberately left open: the routing rule that decides which
outputs go to a person needs a threshold, and a threshold needs an error rate somebody measured.
