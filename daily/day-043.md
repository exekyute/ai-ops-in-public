# Day 043: The SOP finally runs

**Mon 2026-08-03 · Build · Day 43 of 49**

For six weeks this repo has described how a finished build reaches a reviewer: what goes in the packet,
what a queue row holds, what happens when a piece is missing. All of it has been carried out by a person
reading instructions and remembering to follow them. Today one half of that path became a thing that
runs whether or not anybody remembers.

## Shipped

[automations/handoff-intake/](../automations/handoff-intake/), a new folder holding the repo's first
executable automation and its README. The workflow implements the builder's side of
[the handoff SOP](../sops/hand-off-a-build-for-review.md), the documented path a build travels to reach
a reviewer. A builder submits the packet through a form, a Code node re-checks every field against what
the SOP requires, and the branch that follows is the whole point: a complete packet opens a row in the
review queue and notifies the reviewer pool, while an incomplete one is returned with the exact list of
what is missing. The SOP has always said a partial packet is not a handoff. Now something enforces it.

It ships as scrubbed JSON anyone can import, with no credential attached, and it ships inactive.

## What I learned

I had planned this for weeks as "write the log row and the queue row, then notify." Building it meant
reading [the review log spec](../sops/review-log-spec.md), the file defining what one row of the
permanent record holds, closely enough to find that my plan was wrong. The spec says to write the row
when the first review lands, and its handoff-time field spells out the sequence: the queue row carries
that time while a build waits, and it is copied onto the log row as the review is written. A log row
opened at handoff would sit in the permanent record with three of its five required fields empty.

So the handoff half writes one record, not two. That is a small correction with a general shape behind
it. A plan made from memory of a document is not the same as the document, and the gap only shows up
when something has to execute. Prose can say a build "gets logged" and stay true enough to pass. A node
has to pick a table and a moment.

The second thing is what happened when I ran the finished automation through
[this repo's own review checklist](../governance/ai-build-review-checklist.md). It did not get a clean
approve. It came out as approve with fixes, with four real failures: submitting twice opens two queue
rows, a failed write tells nobody, there is one credential with no environment split, and nothing tracks
its volume or exception rate. All four are written into its README rather than quietly left out.

The idempotency one turned out to be the interesting failure. The obvious fix, deduplicating on the
build name, would break a different rule, because
[the handoff ruling](../governance/what-counts-as-one-handoff.md) makes a re-submission a genuine second
arrival that is supposed to get its own queue row. So the fix is a submission id, not deduplication. Two
rules this repo wrote on different days disagree about what a repeat means until you look closely, and
writing the automation is what made anybody look.

## Next

The checklist run above produced a fix list, which is the ordinary outcome of a review and is also the
first time anything here has generated one about itself. What governs that list now is nothing: no rule
says how long a known fix may sit in a README before it stops being a fix and becomes the state of the
build. A repo that has just announced it stops in six days needs to say what happens to its open items
after that, and what it means to call something maintained rather than finished.
