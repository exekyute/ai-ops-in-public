# Day 039: Typing in a box is a deploy

**Thu 2026-07-30 · Document · Day 39 of 49**

Change control assumes somebody made the change. There is a diff, an author, and a date, and you can
put a review in front of all three. A model step breaks that from both ends. Editing its prompt leaves
no diff anywhere, because a prompt is a string in a text box rather than a definition you export. And
some of its changes arrive with no author at all, because the provider made them.

## Shipped

[standards/prompt-and-model-change-control.md](../standards/prompt-and-model-change-control.md), only
the second file in `standards/` and the first addition to the repo's rules in five weeks. It puts six
things under one procedure, the prompt text, the model id and version, the decoding parameters, the
tool definitions, the output schema, and the grounding source, on the grounds that all six change what
the build decides and none of them are covered by section 9 of
[the automation standard](../standards/automation-standards.md), the baseline every build here is
judged against, which was written for workflow definitions. The rules that follow are pinning, watching
for the changes nobody made, re-opening the recorded human placement from
[where a human stays in the loop](../enablement/where-a-human-stays-in-the-loop.md), naming which
review lines a configuration change re-opens and which stand, comparing old and new on the same set of
inputs, and keeping enough of the previous configuration that rollback is a restore instead of a
rewrite. It went into [the review-loop index](../sops/the-review-loop-in-order.md), the start-here page
that orders every piece of the review system, under the builder's row and the reviewer's, taking the
tally to twenty pieces.

## What I learned

The draft went out claiming that change control has no vocabulary for a change with no changer, and
that claim came back refuted. Lockfiles, version ranges, floating container tags, evergreen browsers,
and operating systems that patch themselves all exist precisely because software has always had
changes nobody made. The idea I thought was the file's contribution was a thing every engineer already
solves before lunch.

What survived is narrower and truer. The mechanism is old; the missing signal is new. A library that
moves under you still leaves a diff somewhere, and usually a test that goes red. A model that moves
under you produces prose that still parses, still validates, and still finishes green. So the fix is
the same fix, pinning, adopted for a different reason: not to prevent the change, but to make it an
event at all. Writing the weaker, correct version cost the file its most impressive sentence and made
it worth trusting.

The same read caught a second thing I had assumed. I was treating a pinned model id as a promise about
behavior, and it is not one. Providers move serving stacks and safety filters behind a stable version
id, and none of that produces an event either. That gave the file a rule I would not have written on
my own: re-run the comparison set on a cadence, not only when you change something.

## Next

The rule that a configuration change has to run against a set of inputs rather than a single run is
sitting there without a number attached. The file says to put the case that prompted the change into
the set, and the cases the build has gotten wrong before, and to write down what you actually ran. It
does not say how big the set is, what belongs in it, or what result clears it for release. Those are
measurement questions, and this repo has a place it puts those.
