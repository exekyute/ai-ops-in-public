# Day 040: A passing score on the cases you kept

**Fri 2026-07-31 · Analyze · Day 40 of 49**

Somebody rewrites two sentences of a prompt to fix a case the model kept getting wrong. The next
question is whether the build actually improved, or whether that one case now passes while something
else quietly broke. Answering it means keeping a pile of inputs whose right answers you know and
scoring the model against them. That pile has a name, and it comes with a set of traps.

## Shipped

[analytics/evals-and-the-review-loop.md](../analytics/evals-and-the-review-loop.md), the second memo in
`analytics/` and the file that pays off two debts this repo has been carrying on purpose.
[The placement guide](../enablement/where-a-human-stays-in-the-loop.md), which decides where a person
sits relative to a step that calls a model, declined to say where a routing threshold goes.
[The change-control standard](../standards/prompt-and-model-change-control.md), the rules that put a
prompt and a model version under change control, said a configuration change has to run against a set
of inputs and declined to say how big the set is or what clears it. Both wanted the same object.

The memo says what the set holds: a regression list of every case that ever caused a change, whose bar
is every case passing with no threshold, and a representative list drawn to look like live traffic,
whose bar is a rate. It gives the regression list a retirement rule, since a list that only grows
eventually blocks every change, so a case leaves it in writing with the change that made it wrong. It
gives the representative list a sizing floor, and it separates two thresholds that had been collapsed
into one: the release bar that clears a change, and the routing line that decides which live outputs
reach a person. Drawing that second one needs a field recorded on every case from the first case on. It
also settles where an eval sits against
[this folder's own ruling](../analytics/measure-or-test.md) on when a question wants a number and when
it wants a test, and it went into [the review-loop index](../sops/the-review-loop-in-order.md), the
start-here page ordering every piece of the review system, taking the tally to twenty-one pieces.

## What I learned

I went in with a tidy result and it was wrong. The placement guide asks two questions, one about
whether a wrong output can be undone and one about whether anything would notice it. My claim was that
an eval moves the second and never the first. The first half does not survive contact with the guide's
own wording. Its strongest detection answer reads "a machine rejects it, every time," and adds that if
a wrong answer can be a valid member of the set your validator allows, the answer does not apply. That
is a claim about every wrong answer, including the ones nobody has written down, and a sample cannot
certify a claim about everything. An eval is a sample by construction, which the same memo spends its
opening section establishing. My result contradicted my own argument two sections earlier.

What replaced it is asymmetric and more useful. An eval can refute a detection answer and cannot
establish one. A single case where the validator waved through a wrong answer settles the question on
the spot. A clean sweep of the whole set proves nothing about the wrong answers nobody thought to
collect. Establishing the strong answer takes a different kind of evidence entirely, an argument about
how the gate is built, a closed set of allowed values, an id that has to resolve, which is something a
reviewer settles by opening the step rather than by reading a score.

The general form is worth keeping. A sample is worth more as a refutation than as a confirmation, and a
set that has only ever passed has told you nothing you can lean on. The repo has said a version of this
before, in [the index check's own notes](../checks/README.md), which record that three failures were
deliberately planted and run because a check that has only ever passed is a check nobody should trust.
Same shape, one level out.
